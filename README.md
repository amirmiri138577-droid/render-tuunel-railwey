# PasarGuard Node — Railway / Fly.io / Render / VPS Deployment

This repository is a portable Docker wrapper around the official [PasarGuard Node](https://github.com/PasarGuard/node) image. It is **not the PasarGuard panel**. It runs one node that can be connected from any reachable PasarGuard panel, whether that panel is on Railway, a VPS, or another Docker host.

## What this version fixes

- Pins the upstream node image to `pasarguard/node:v0.5.4` instead of the moving `latest` tag.
- Works on Railway, Fly.io, Render Web Services, and ordinary Docker/VPS deployments.
- Uses `NODE_PUBLIC_HOST` for the TLS certificate SAN instead of assuming Railway private DNS.
- Uses Railway `PORT` only as a fallback; an explicit `SERVICE_PORT` always wins.
- Requires and validates a real UUID `API_KEY`.
- Persists the API key and generated certificate under `/var/lib/pg-node`.
- Regenerates only certificates generated by this wrapper when the public hostname changes.
- Saves connection details in `/var/lib/pg-node/connection-info.txt`.
- Keeps the official gRPC/TLS node API, so the panel does not need a custom client.

## Render deployment

This repository includes [`render.yaml`](render.yaml) for a **free Render Web Service**. The entrypoint starts a tiny HTTP health server on Render's injected `PORT`; the PasarGuard gRPC listener remains on `SERVICE_PORT=62050` and user traffic is forwarded by Rathole.

### Deploy from the Render Dashboard

1. In Render, choose **New → Blueprint** and select this GitHub repository.
2. Select the branch `main` and apply the Blueprint.
3. Render creates a Web Service named `pasarguard-node` and checks `/health`.
4. In the service's **Environment** settings, set:

   ```text
   NODE_PUBLIC_HOST=<the Railway relay data hostname used by the panel>
   API_KEY=<a valid UUID>
   ```

   Keep these values secret. `SERVICE_PORT` is already set to `62050`.
5. Deploy the service and open **Logs**. The node prints Address, Port, API key and certificate on the first boot (or when `FORCE_PRINT_CONNECTION_INFO=true`).
6. Confirm the logs contain `Render health server listening`, `gRPC Server listening`, and `starting Rathole client`.

### Render free-plan limitations

Render's public Web Service endpoint is HTTP/HTTPS only and is used here only for `/health`; PasarGuard gRPC and user TCP traffic use the outbound Rathole tunnel to Railway. The free plan has no persistent disk and may sleep, so keep `API_KEY` fixed in Environment Variables and expect a newly generated self-signed certificate after a fresh instance is created. Save the new certificate in the panel if it changes. A paid service with a disk or a VPS is more stable.

## Fly.io deployment

The repository includes [`fly.toml`](fly.toml). It exposes the official PasarGuard Node gRPC/TLS listener as raw TCP and mounts a persistent volume at `/var/lib/pg-node`.

### Deploy from a phone or terminal

1. Install/login to Fly.io and create an app with a unique name. Open `fly.toml` and replace:

   ```toml
   app = "pasarguard-node-change-me"
   ```

   with a unique name, for example `pg-node-myserver-123`.
2. Create the Fly app without deploying a second time:

   ```bash
   fly apps create pg-node-myserver-123
   ```

3. Allocate a persistent volume in the same region as `primary_region`:

   ```bash
   fly volumes create pg_node_data --region ams --size 1 --app pg-node-myserver-123
   ```

4. Set the two secrets. `NODE_PUBLIC_HOST` must be the hostname that the panel will use:

   ```bash
   fly secrets set \
     NODE_PUBLIC_HOST=pg-node-myserver-123.fly.dev \
     API_KEY=xxxxxxxx-xxxx-4xxx-8xxx-xxxxxxxxxxxx \
     --app pg-node-myserver-123
   ```

5. Deploy:

   ```bash
   fly deploy --app pg-node-myserver-123
   ```

6. Read the first-boot details:

   ```bash
   fly logs --app pg-node-myserver-123
   ```

### Values in the PasarGuard panel

Use the Fly hostname and the public port from `fly.toml`:

```text
Address: pg-node-myserver-123.fly.dev
Port: 62050
API Port: 62050
Connection type: grpc
API key: the API_KEY secret
Certificate: the complete PEM printed by the node
```

### Fly.io networking rules

- Do not add `handlers = ["tls"]` to the TCP service. Fly must pass the TLS bytes through unchanged because PasarGuard Node terminates TLS itself.
- Keep one machine when using the single volume.
- For IPv4-only clients, allocate a dedicated IPv4 if required by your network:

  ```bash
  fly ips allocate-v4 --app pg-node-myserver-123
  ```

- This file exposes the **node control API** on port `62050`. Xray/WireGuard user traffic may use additional inbound ports created by the panel. Those ports must also be exposed in Fly and are not automatically made public by the control API service. For full data-plane deployment, use a VPS or add the required Fly service port definitions for the actual inbound ports.

## Railway deployment

1. Create a new Railway project.
2. Deploy this GitHub repository as a service.
3. Attach a Railway Volume with mount path:

   ```text
   /var/lib/pg-node
   ```

4. Configure a public TCP endpoint/proxy to the service port. Set `SERVICE_PORT` to the internal port selected by the proxy. If Railway supplies a runtime `PORT` and `SERVICE_PORT` is not set, the entrypoint uses `PORT` automatically.
5. Set the following variables:

   ```text
   NODE_PUBLIC_HOST=<the public hostname used by the panel>
   SERVICE_PROTOCOL=grpc
   API_KEY=<a valid UUID, recommended>
   ```

   `NODE_PUBLIC_HOST` must be a bare hostname or IPv4 address, for example `node.example.com`; do not include `https://` or `:port`.
6. Deploy once and copy the complete certificate from the deployment log, or read it from `/var/lib/pg-node/connection-info.txt`.
7. In any PasarGuard panel, add a node using the displayed address, port, API key and complete PEM certificate.

### Important Railway networking rule

`RAILWAY_PRIVATE_DOMAIN` is reachable only by services in the same Railway project/environment. It is **not** a public address for a panel running on a VPS. For a panel outside Railway, use a public TCP endpoint and set `NODE_PUBLIC_HOST` to that public hostname.

## VPS / Docker deployment

```bash
docker volume create pasarguard-node-data

docker build -t pasarguard-node .
docker run -d \
  --name pasarguard-node \
  --restart unless-stopped \
  -p 62050:62050 \
  -v pasarguard-node-data:/var/lib/pg-node \
  -e NODE_PUBLIC_HOST=node.example.com \
  -e SERVICE_PORT=62050 \
  -e API_KEY=xxxxxxxx-xxxx-4xxx-8xxx-xxxxxxxxxxxx \
  pasarguard-node
```

For an IP address, use the IP in `NODE_PUBLIC_HOST`; the generated certificate receives an IP SAN. For a domain, point DNS to the VPS first and use the domain in the variable.

## Panel connection values

Use these values in the node form of the panel:

| Field | Value |
|---|---|
| Address | The exact `NODE_PUBLIC_HOST` printed by the node |
| Port | `SERVICE_PORT` printed by the node |
| Protocol | gRPC for the standard official node client |
| API key | The UUID printed once or supplied through `API_KEY` |
| Certificate | The complete PEM certificate, including `BEGIN CERTIFICATE` and `END CERTIFICATE` |

The panel must be able to route to the address and port. The TLS certificate hostname must match the address entered in the panel.

## Render Node + Railway Panel through Rathole tunnel

This repository also contains `railway-relay/`. Use this only when the Node must run on Render while the PasarGuard panel runs on Railway.

### 1. Deploy the relay on Railway

Create a **separate Railway service** from this repository and set its Dockerfile path to:

```text
railway-relay/Dockerfile
```

Add this secret variable to the relay:

```text
RATHOLE_TOKEN=<one-long-random-secret>
```

Create **two TCP Proxies** for the relay service:

| Purpose | Internal port | Used by |
|---|---:|---|
| Rathole control | `2333` | Render Node tunnel client |
| PasarGuard Node data | `62050` | PasarGuard panel |

Copy each generated `host:public-port`. The control address goes into `RATHOLE_SERVER_ADDR`; the data address is the address entered in the panel.

### 2. Deploy the Node on Render

Deploy the main repository as a Render Web Service with the persistent disk `/var/lib/pg-node`. Add these variables:

```text
SERVICE_PORT=62050
SERVICE_PROTOCOL=grpc
TUNNEL_ENABLED=true
RATHOLE_SERVER_ADDR=<relay-control-host>:<relay-control-public-port>
RATHOLE_TOKEN=<the-exact-same-secret-as-the-relay>
NODE_PUBLIC_HOST=<relay-data-host>
API_KEY=<valid-UUID>
```

`NODE_PUBLIC_HOST` must be the **relay data hostname**, not the Render hostname, because the certificate is presented through the tunnel to the panel.

### 3. Add the node in the Railway panel

Use the relay data proxy values:

```text
Address: <relay-data-host>
Port: <relay-data-public-port>
API Port: <relay-data-public-port>
Protocol: grpc
API Key: the Render API_KEY
Certificate: the complete PEM printed by the Render logs
```

The Render Node initiates the tunnel outbound, so Render does not need a public TCP port. Never expose the Rathole token in the panel or a public repository.

### Tunnel limitations

This mapping forwards the PasarGuard Node control/data port `62050`. If the panel creates separate Xray or WireGuard listener ports, those ports need additional Rathole service mappings and additional Railway TCP Proxies; they are not automatically forwarded by this one mapping. For a full multi-port data-plane deployment, a VPS remains simpler.

## Environment variables

See [.env.example](.env.example) for all supported variables. The upstream image also supports the official `PG_NODE_WG_*` variables.

## Security notes

- Prefer setting `API_KEY` explicitly in Railway/VPS secrets.
- Do not publish the certificate and API key together in a public issue or chat.
- Keep `/var/lib/pg-node` persistent; otherwise the generated key/certificate can change after redeploy.
- The API key is intentionally printed only when a new key/certificate is created. Use `FORCE_PRINT_CONNECTION_INFO=true` for a controlled reprint.
- WireGuard host routing may require Linux kernel capabilities unavailable on some managed platforms. The node API can be reachable even when WireGuard data-plane features are not supported.

## Upgrade the upstream node

The image is pinned for reproducibility. To upgrade, change the `PASARGUARD_NODE_IMAGE` build argument in the Dockerfile to an existing upstream version, test panel compatibility, and redeploy. Do not silently switch back to `latest` in production.
